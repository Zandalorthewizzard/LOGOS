# GLM 5.1 Agent Profile

## Purpose

Define the project-local execution model for `GLM 5.1` so task sizing, report format, and review posture stay consistent across passes.

## Summary Judgment

`GLM 5.1` is a workable bounded implementation agent. It is productive on narrow slices, but it is not reliable enough to self-certify closure on broad protocol or runtime contracts.

## Strengths

1. Moves code forward instead of stalling in discussion.
2. Performs reasonably well on tightly specified happy-path implementation work.
3. Follows the existing architecture lane when decisions are already locked.
4. Can make useful progress on one closely related runtime or protocol slice at a time.

## Weaknesses

1. Overclaims completion in reports.
2. Treats narrow proof tests as if they close the full contract.
3. Distinguishes poorly between `implemented`, `partially working`, and `contract-complete`.
4. Can silently ignore request fields or sub-modes if tests do not assert them explicitly.
5. Is weaker on product/runtime semantics than on local code motion.

## Best Use Cases

Use `GLM 5.1` for:

1. One bounded implementation slice with one closely related concern set.
2. Contract-tightening passes where the missing behavior is already known.
3. Narrow adapter, runtime, or app-server fixes with explicit proof targets.
4. Follow-up passes driven directly by review findings.

## Do Not Use It For

1. Wide multi-surface implementation passes.
2. Open-ended architecture design.
3. Large ambiguous parity pushes with many optional branches.
4. Final acceptance judgment without external review.

## Optimal Slice Size

1. One pass should usually cover one surface or one tight control cluster.
2. If the slice touches multiple operations, they should share the same runtime contract.
3. If the contract has several request modes, split implementation from contract-honesty cleanup when needed.
4. Prefer two narrow passes over one broad pass.

## Tasking Rules For This Agent

When `GLM 5.1` is the execution agent:

1. Lock decisions up front. Do not leave design alternatives open in the task.
2. State explicit non-goals.
3. Require exact proof tests, not generic "add tests".
4. Ask for explicit unsupported modes if any remain.
5. Require direct answers about contract behavior, not only a prose summary.
6. Ask for changed crates/files, not a vague changelog.
7. Require explicit residual-risk and adjacent-open-surface accounting instead of letting the report imply broader closure.
8. Require an explicit parity remainder so the report states what still remains toward maximum realizable parity and why it is not in this slice.

## Acceptance Posture

1. Do not accept `slice closed` at face value.
2. Independently inspect whether request fields, config knobs, and sub-modes are actually honored.
3. Re-run only the key proof tests needed to confirm or reject the closure claim.
4. Use review findings to cut the next pass even narrower if the report overclaims.
5. Check the report against `2026-04-18-slice-risk-register-and-boundary-discipline.md` before accepting closure.
6. Check that the report names the remaining path to maximum realizable parity, not just residual risks.

## Mandatory Report Template

Embed this template in future task messages to `GLM 5.1`:

```text
Return format:
1. `Closed`
   - what was actually implemented
2. `Still Explicitly Unsupported`
   - exact modes or operations that remain unsupported after this pass
3. `Blocked`
   - what could not be implemented honestly, with exact reason
4. `Changed crates/files`
5. `Tests/checks run`
6. `Verdict`
   - `slice closed`
   - or `still blocked by <exact blocker>`
7. `Explicit answers`
   - <contract question 1>
   - <contract question 2>
   - <contract question 3>
8. `Residual risks`
   - <adjacent-open surface 1>
   - <transitional residue>
   - <stale owner or seam risk>

9. `Parity remainder`
   - <maximum parity surface still open>
   - <why it is not in this slice>
   - <follow-up slice or blocker>
```

## Orchestrator Response Model

After each `GLM 5.1` pass, the orchestrator should answer in this order:

1. `Findings`
2. `Verification`
3. `Verdict`

This is mandatory when:

1. the pass changes protocol behavior,
2. the pass claims parity or closure,
3. request modes can be ignored silently,
4. unsupported behavior is being narrowed.

## Practical Operating Model

1. Use `GLM 5.1` as a worker, not as the final acceptance authority.
2. Feed it the next slice from roadmap/spec plus the latest review findings.
3. Keep it in one language per loop; English tasking is preferred for consistency.
4. Keep the task dry, exact, and alternative-free.
5. If it overclaims, answer with a narrower corrective pass instead of widening scope.

## Recommended Default Task Shape

1. One sentence naming the slice.
2. Branch name.
3. Locked decisions.
4. Read-first list.
5. Exact implementation requirements.
6. Explicit non-goals.
7. Required risk register.
8. Required parity remainder.
9. Required tests and proofs.
10. Mandatory report template.
